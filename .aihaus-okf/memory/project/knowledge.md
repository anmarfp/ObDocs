# Knowledge — DocsObs

> Durable facts, architectural conventions, and technical gotchas.

## Current truth

- **HTML Table Rule in Prototypes:** Flex container utility classes (`display: flex`) must NEVER be applied directly to `<td>` tags, as doing so breaks standard table cell rendering layout (`display: table-cell`) and misaligns column headers across `<thead>` and `<tbody>`. Flex layout must always be applied to an inner `<div>` wrapper placed inside the `<td>`.
- **Status Calculation Logic (RN-001):**
  - ⚪ `INDETERMINATE`: `expiration_date` is NULL or category is "Sem Vencimento".
  - 🔵 `RENEWAL_IN_PROGRESS`: Manual status is "Em Renovação".
  - 🔴 `EXPIRED`: Current Date > `expiration_date`.
  - 🟡 `CRITICAL`: (`expiration_date` - Current Date) <= `alert_lead_days`.
  - 🟢 `REGULAR`: Current Date < `expiration_date` and outside lead days.
- **Context-Rich Prompting for Specialist Agents (Planner/Implementer/Reviewer):** When creating agent sessions via Orca CLI, the initial prompt must be exhaustive and structured: provide the project domain (DocsObs), full business rules (RN-001 to RN-009), exact file/schema references (`backend/prisma/schema.prisma`, `backend/src/routes/*`, `frontend/styles.css`), technical constraints (strict TS, 10MB limits, RBAC) and clear verification checkpoints.
- **`main` is the de facto integration branch; there is no CI/CD pipeline yet.** No `.github/workflows/` exists — "post-merge pipeline" is currently just `npm run test:all` run locally. `git remote` only has `origin/main` (plus stale `origin/Criar-o-protótipo-da-UI`) — no `develop`/`staging` branch was ever created.
- **Gotcha — `Agent(isolation: "worktree")` can branch from a stale base, making a raw `git diff main` inside it lie.** The worktree is not guaranteed to fork from the orchestrator's current local `HEAD` — if the orchestrator made a local commit on `main` that hadn't been pushed yet, the delegated agent's branch can still be based on the previous (already-pushed) tip. A `git diff main` run inside that worktree then shows every file from the orchestrator's unpushed commit as **deleted**, which looks like the subagent destroyed work but is actually just base drift. **Diagnose with `git log --oneline -5` inside the worktree (does the orchestrator's planning commit appear as an ancestor?) and `git diff $(git merge-base HEAD main) HEAD --stat`** (the true, isolated diff of the agent's own work) before concluding anything was deleted. Fix by merging `main` into the agent's branch before finishing the review — this can silently recreate a file at its pre-subtask path if the same task file was independently added on both sides (e.g. a kanban card in `backlog/` on `main` and moved to `doing/` by the agent) — check for and remove the duplicate after merging. Observed 2026-08-30 during DOC-28 subtask 1 (card `T-260830-6vz64a`).
- **Gotcha — pre-existing flaky test tied to the wall-clock date.** `backend/tests/notification-gcal.test.ts` (`cronService` › "recalcula documentos ativos...") hardcodes a fixture with `expirationDate: new Date('2026-08-30T00:00:00.000Z')` expecting status `CRITICAL`, without freezing the system clock (no `vi.setSystemTime`/fake timers). It fails whenever the real date reaches on/after 2026-08-30 (the fixture becomes `EXPIRED` instead), and will very likely start passing again once the date has moved past it — until it drifts stale again. Confirmed 2026-08-30 failing identically on plain `main` with no other changes (not a regression from DOC-28 subtask 1). Needs `vi.useFakeTimers()`/`vi.setSystemTime()` pinning "today" to fix properly; out of scope for DOC-28, left as a known pre-existing issue.
- **Gotcha — when correcting a delegated agent's work in its worktree, edit files by the worktree's absolute path, not the primary checkout's.** During DOC-28 subtask 2 review, a kanban-card Log note was written with `file_path` under the primary checkout (`C:\...\ObDocs\.aihaus-okf\...`) while `cwd` was inside the agent's worktree (`...\.claude\worktrees\agent-<id>\...`) — the two are separate working trees of the same repo, so the edit silently landed in the wrong copy, wasn't included in the `git add`/commit run from the worktree, and surfaced later as an unrelated-looking merge conflict when pulling the merged PR into the primary checkout. Always double-check which working tree a file edit is targeting when a subagent's worktree and the primary checkout are both in play in the same review pass.
- **Gotcha — `gh pr merge --delete-branch` silently skips the remote branch deletion when the local branch delete fails.** If the merged PR's branch is still checked out by an active `git worktree` (common right after merging from inside that worktree), the command reports a `failed to delete local branch ... used by worktree` error and does NOT delete the branch on GitHub either — it looks like only the local step failed, but `gh api repos/<owner>/<repo>/branches` confirms the remote branch is still live too. Verify with `git branch -r` (after `git fetch origin --prune`) or the `branches` API after any `gh pr merge --delete-branch`, and clean up leftover remote branches manually (`gh api -X DELETE repos/<owner>/<repo>/git/refs/heads/<branch>`) once the worktree is actually removed. Observed 2026-08-30 across all 5 DOC-28 subtask branches.
- **Gotcha — never set a hardcoded default `Content-Type: application/json` header on the shared `axios` instance (`frontend/src/services/api.ts`).** Doing so makes axios's `transformRequest` `JSON.stringify()` any `FormData` payload instead of sending it as `multipart/form-data` (axios only auto-detects `FormData` and skips JSON serialization when no conflicting `Content-Type` is already set). This silently destroyed file uploads (DOC-29: attaching a PDF on document create/edit never persisted, because `multer` on the backend never saw a real multipart body). Let axios infer `Content-Type` per request instead — it already sets `application/json` for plain objects and the correct multipart boundary for `FormData` on its own. No test caught this because `backend/tests/*.test.ts` use `supertest().attach(...)`, which builds a real multipart request directly at the HTTP layer, bypassing the frontend's axios instance entirely — this bug class is only visible from a real browser/axios client, not from backend-only tests.
- **Gotcha — `orca worktree create --agent codex --prompt "<text>"` mangles multi-line prompts on Windows.** Codex is launched through `cmd.exe`, which caret-escapes the prompt argument; backticks, double quotes, and parentheses in a multi-line prompt get corrupted, and codex's own CLI arg parser then misinterprets a stray word as a subcommand (`error: unrecognized subcommand 'pagina'`) and exits immediately — the worktree/terminal is created fine, but codex never actually starts working. **Fix:** create the worktree with `--agent codex` but no working `--prompt` (or let the botched one fail), then once the terminal drops back to a plain shell, `orca terminal send --text "codex --dangerously-bypass-approvals-and-sandbox" --enter` to launch it interactively, wait for the TUI, and send the actual task prompt via a *separate* `orca terminal send --text "<prompt>" --enter` call — plain prose (avoid backticks/parens/curly-quotes; spell out symbols in words) sent this way reaches codex intact. Observed 2026-09-01 delegating DOC-35 and DOC-30.
- **Gotcha — Codex's shared `config.toml` can get corrupted by concurrent launches on Windows.** Launching two `codex` processes near-simultaneously (e.g. two `orca worktree create --agent codex` calls back to back) can leave `%APPDATA%\orca\codex-runtime-home\home\config.toml` with a huge run of NUL bytes prepended to its real content, which then fails to parse (`Error loading config.toml: ... key with no value, expected =`) and crashes every subsequent codex launch, not just the ones that raced. Safe to repair: back up the file, then strip the leading NUL run — the trailing content (`[projects...]`, `[hooks.state...]`) is untouched local runtime metadata, not secrets. Observed 2026-09-01.
- **Gotcha — `orca terminal wait --for tui-idle` is unreliable for a codex TUI on Windows; it can report `satisfied: true` while codex is still actively working** (mid tool-call, spinner still animating). Don't trust a single wait result as "done" — cross-check `orca terminal show`'s `title` field: while codex is busy the title is prefixed with a braille spinner glyph (⠋⠙⠹⠸⠼⠴⠦⠧⠇⠏); poll (e.g. a `until ... ; do sleep 10; done` loop backgrounded via Bash) until that glyph disappears before reading the terminal for a final result. Observed 2026-09-01.
- **Gotcha — codex's "Update available" prompt on launch blocks scripted answers.** `orca terminal send` refuses ordinary text (e.g. `"2"` for "Skip") aimed at this specific prompt with `agent_prompt_blocked` — but a bare `--text "" --enter` (plain Enter) passes through and safely dismisses it without triggering the actual `npm install -g @openai/codex` update. Observed 2026-09-01.
- **Gotcha — dirty Orca worktrees are not automatically unmerged work.** The 4 reusable pipeline worktrees (`anmarfp/planner-frontend`, `anmarfp/reviewer-codex`, `anmarfp/implementer-antigravity`, `anmarfp/qa-codex`) were never merged into `main` via PR/merge commit — a prior orchestrator run applied the vetted final diffs **directly onto `main`** as regular commits (Phase 3/4: `62b05f8`, `7682cd2`, `f74c83f`, `d13cb43`, `b0463ea`), leaving those branches behind `main` (0 unique commits each) with stale uncommitted working-tree changes from mid-pipeline. Verified 2026-08-29: `git -C <worktree> rev-list --left-right --count main...HEAD` showed `N 0` for all four (zero unique commits), and a full per-file diff of every `M`/`??` path against `main`'s current content showed the deltas were either byte-identical or strictly older/superseded snapshots (e.g. `implementer-antigravity`'s `docker-compose.yml` still used `localhost` health-checks that `main` later fixed to `127.0.0.1`). **Before treating a worktree's dirty status as pending work to merge, diff every changed file's content against `main`, not just `git status`.**
